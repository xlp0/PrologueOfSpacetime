# SHOPPER ANALYTICS — Hardware & Computational Benchmarks

> **Last Benchmarked:** 2026-04-06
> **Server:** `hpserver` (Ubuntu 24.04 LTS)

This document formally records the exact hardware constraints of the deployment system, the mathematical processing payload generated by the local YOLOv11n (Nano) Vision API array, and the physical store coverage achieved by the sensor network.

---

## 1. Physical Hardware Capabilities

| Component | Specification |
|---|---|
| **Processor** | Intel Core i5-2400 @ 3.10 GHz |
| **Architecture** | 2nd-Gen "Sandy Bridge" (Q1 2011) |
| **Cores / Threads** | 4 Cores / 4 Threads |
| **RAM** | 32 GiB DDR3 (31 GiB allocatable) |
| **GPU** | Intel HD 2000 Integrated (no CUDA/OpenCL AI acceleration) |
| **OS** | Ubuntu 24.04 LTS |

> [!WARNING]
> **No AVX2 / AVX-512 / NNPACK Support**
> This CPU predates AVX2 and FMA3 instructions. PyTorch will log `[NNPACK.cpp:56] Could not initialize NNPACK!` on every boot. The inference pipeline bypasses this via pure x86 FP32 fallback paths. DeepSORT was removed entirely and replaced with a **pure-Python IoU tracker** to eliminate all native-lib crashes on this hardware.

## 2. Model Computation (TFLOPs FP16)

The inference pipeline runs three independent YOLO workers — one per camera — each capped to 1 PyTorch thread to prevent CPU starvation.

### Baseline Reference
| Parameter | Value |
|---|---|
| **Model** | YOLOv11n (Nano) |
| **Parameters** | ~2.62 Million Weights |
| **Standard Load (640×640)** | ~0.0065 TFLOPs FP16 per frame |

### Current Optimised Configuration

To prevent ffmpeg from being starved of CPU time (which caused stream disconnects), YOLO inference was reduced as follows:

| Parameter | Original | Current (Optimised) |
|---|---|---|
| **Input Size** | 640×640 | **320×320** |
| **FLOPs per frame** | 0.0065 TFLOPs | **~0.00163 TFLOPs FP16** |
| **Inference Rate** | ~5 FPS | **~2 FPS per camera** |
| **PyTorch Threads** | default | **1 thread per worker** |

> [!NOTE]
> A 320×320 input reduces the pixel surface area by **75%** vs 640×640, cutting per-frame compute to approximately **0.00163 TFLOPs FP16**.

## 3. Total System Throughput

$$\text{Total Load} \approx 3 \text{ Cameras} \times 2 \text{ FPS} \times 0.00163 \text{ TFLOPs FP16}$$

$$\boxed{\text{Total Load} \approx \textbf{0.00978 TFLOPs FP16 continuous}}$$

This leaves sufficient CPU headroom for:
- 3× `ffmpeg` H.264 encoding processes (RTSP → MediaMTX → HLS)
- FastAPI WebSocket server (port 5000)
- Dual LiDAR WebSocket stream parser
- Dashboard rendering (browser-side, no server load)

## 4. Physical Coverage Area

The camera and LiDAR network covers the following store zones:

| Axis | Range | Description |
|---|---|---|
| **Depth (Y)** | 0 m → 12 m | Entrance (0m) to Back Wall (12m) |
| **Width (X)** | 0 m → 3.5 m | Left wall to right wall |

$$\text{Total Coverage Area} = 12\text{m} \times 3.5\text{m} = \boxed{42 \text{ m}^2}$$

### Sensor Placement

| Sensor | Position | Coverage Zone |
|---|---|---|
| **CAM-1** (Entrance) | Right wall, Y ≈ 0–2m | Entrance zone |
| **CAM-2** (Back-Left) | Back-left wall, Y ≈ 10–12m | Back-wall zone, left side |
| **CAM-3** (Back-Right) | Back-right wall, Y ≈ 10–12m | Back-wall zone, right side |
| **LiDAR Sensor-1** | Ceiling centre, Y ≈ 6m | Full-width sweep (360°) |
| **LiDAR Sensor-2** | Ceiling centre, Y ≈ 6m | Phase-offset 180° (fills blind spots) |

### Homography Calibration Points (per camera)
Each camera uses a 4-point homography matrix to convert pixel coordinates to real-world floor metres. Calibration points are stored in `src/homography_fusion/calibration_points.json`.

## 5. System Configuration & Scaling (.env)

The system dynamically pulls hardware constraints and sensor paths natively from the `.env` environment file. If you are upgrading to a stronger machine (e.g., equipped with an NVIDIA RTX 4090 or Apple M4 Max), you can effortlessly scale the tracking network here without modifying any source code.

**`/home/hpserver/SHOPPER-ANALYTICS/.env`**
```env
# Upgrade from yolo11n.pt to yolo11x.pt (eXtreme) on capable hardware
YOLO_MODEL=yolo11n.pt

# Map physical RTSP feeds flexibly
CAM_1_URL=rtsp://admin:password@10.0.0.1:554/cam1
CAM_2_URL=rtsp://admin:password@10.0.0.2:554/cam2
CAM_3_URL=rtsp://admin:password@10.0.0.3:554/cam3
```

> [!TIP]
> **GPU Activation:** Upgrading to `YOLO_MODEL=yolo11x.pt` on a CUDA-enabled machine will automatically latch onto the NVIDIA accelerator, instantly freeing the CPU and enabling full 640x640 processing at >30 FPS per camera.

## 6. Tracking Pipeline Summary

| Stage | Technology | Notes |
|---|---|---|
| **Object Detection** | YOLOv11n (Ultralytics) | Class 0 (person) only, `conf ≥ 0.35` |
| **Tracking (per camera)** | Pure-Python IoU Tracker | No native libs, no crashes on i5-2400 |
| **Spatial Fusion** | Euclidean clustering (0.8m threshold) | Merges overlapping camera detections |
| **Global Re-ID** | JavaScript Global Memory Matrix | Assigns persistent `G-XX` IDs across cameras |
| **Trail Persistence** | Timestamp-based position buffer | Trails kept indefinitely; expire after **20s** of no detection |
